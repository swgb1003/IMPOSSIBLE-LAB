# IMPOSSIBLE LAB — 完全開発仕様書 v2.0（デザイン確定・Claude Code実装版）

> 想像を、体験できる発明に。  
> 対象：卒業制作（12週間）／Unity・Meta Quest 3S／日本語UI  
> 更新日：2026-11-04

## 0. 本書の使い方

本書はCodex / Claude Codeに渡す開発用仕様書。**MUST** は卒業制作の必須要件、**SHOULD** は時間が許す限り実装、**FUTURE** は卒業制作後の構想。実装前に環境・APIの利用条件を確認する。各フェーズは完了条件を満たしてから次へ進む。

## 1. ビジョンと社会課題

### 1.1 コンセプト

利用者が日本語で発明したい道具を説明すると、AIが構造と機能を設計し、VR研究室で動作する3D試作品を組み立てる。利用者は道具を使用し、実験で問題を発見し、自然言語で改良する。DREAM MODEでは空想的な機能を体験し、REALITY MODEでは限定的な物理モデルと実現上の制約を可視化する。

### 1.2 解決を目指す課題

試作品制作には設計・プログラミング・3Dモデリング等の技能と費用が必要で、生活上の困りごとを持つ人が自らアイデアを試すハードルが高い。IMPOSSIBLE LABは**仮想試作への参加障壁**を下げる。現実の製品としての実現可能性・安全性を保証しない。

### 1.3 対象ユーザー

- 主対象：10〜20代のものづくり初心者、学生、創作好き
- 副対象：生活上の不便を改善したい人、教育関係者、地域の課題解決に関心のある人
- 代表ユースケース：手を使わず雨を防ぐ装置の試作、荷物運搬ロボット、空飛ぶ靴

### 1.4 独自性の仮説

自然言語で**機能付き試作品を構築**し、VRで**身体的に試用**し、実験結果から**再設計**し、**空想と現実の制約を比較**する体験を一体化する。世界初の主張はしない。先行研究・既存サービス・特許の調査を別途行う。

## 2. スコープと優先順位

### MUST（発表で必ず動く）

1. Quest 3S上で動作するVR研究室（座位・立位を選択可能）
2. 日本語テキスト指示による発明設計、音声は代替可能な拡張機能
3. LLMが制約付きJSONの発明設計図を出力
4. 既存の機能部品から3D試作品を組み立てる
5. 発明品を掴む・配置する・起動する／対応する場合は装着する
6. 自然言語によるパラメータ変更と部品追加・削除（許可された範囲）
7. 実験結果の数値記録と変更前後の比較
8. DREAM / REALITYの切替と違いの明示
9. 発明DNAの保存・読み込み・履歴
10. 社会課題ミッション1件（ハンズフリー雨具）
11. ネットワーク障害時のサンプル設計図読み込み

### SHOULD（余力があれば）

- 音声入力と音声フィードバック
- 雨・風・障害物の実験場を発明カテゴリに合わせて切替
- 3カテゴリ（防護・運搬・移動）すべての完成度向上
- 生成3D外観を固定機能骨格に装着する試験的連携
- 現実化のための参考技術・課題の説明（根拠と不確実性を明示）

### FUTURE（3か月の必達範囲外）

- 未知の機構・動作コードの完全自動生成
- あらゆる道具の高精細3D生成と自動リギング
- 多人数共同発明、作品公開・派生、現実製造データ出力
- 実製品の安全性を保証する工学シミュレーション

### スコープ縮小の順番

遅延時は 3D生成AI連携 → 音声 → 3カテゴリ同時完成 → 高度な演出 の順に削る。**AI指示→動く試作品→実験→改良**の一本の流れは削らない。

## 3. ユーザー体験と画面・空間設計

### 3.1 基本フロー

起動 → 研究室 → 発明指示 → AI設計プレビュー → 3D組み立て → 試用 → 実験場 → 計測 → 改良指示 → 差分確認 → 再実験 → 保存 → 現実化の課題表示。

### 3.2 シーン構成

| Scene | 役割 | 必須UI/機能 |
|---|---|---|
| Boot | 起動・環境チェック | 接続状態、ロード、再試行 |
| Hub | 発明の拠点 | 発明入力、作品棚、チュートリアル、モード表示 |
| Workshop | 発明品の組み立てと編集 | 設計プレビュー、組み立て演出、掴む・起動・改良 |
| TestZone | 発明品を試す | 実験開始/停止、環境設定、結果パネル |
| RealityBridge | 現実的制約の説明 | 仮定、制約、参考技術、検証の限界 |

**実装簡略化：** Unityでは1シーン内のエリア切替でもよい。シーンロード時のVR酔いを避けるためフェードを使用。

### 3.3 画面・パネル

- 発明入力：日本語テキスト、送信、サンプル指示、AI処理中表示
- 設計プレビュー：名前、目的、主要部品、動作、制約、承認/再生成
- 発明操作：掴む、置く、起動、停止、編集、保存
- 実験パネル：環境プリセット、パラメータ、開始/停止、リセット
- 結果パネル：成功/失敗、計測値、前回との差分、次の改良案
- 作品棚：保存済み発明、バージョン、読み込み、複製
- 現実化パネル：仮想挙動と現実的制約を明確に分離

### 3.4 UI/UXルール

日本語、可読性優先、過度なネオン・発光・AI風グラデーションを避ける。落ち着いた工業デザイン。文字は十分大きく、主要操作はコントローラーで完結。長文入力はデスクトップの管理画面やサンプル入力でも代替できるようにする。座位/立位対応、テレポート移動、スナップターン、視界暗転、VR酔いに配慮した飛行デモを提供。

## 4. 技術アーキテクチャ

```text
Quest 3S (Unity / OpenXR / XR Interaction Toolkit)
  ├─ UI / VR Interaction
  ├─ Invention Builder (parts + behavior modules)
  ├─ Experiment Runner / Telemetry
  ├─ Mode Controller (Dream / Reality)
  └─ Local JSON persistence
          │ HTTPS (optional network)
          ▼
    Backend API (API key stored server-side)
          ├─ LLM design / edit request
          ├─ Schema validation / whitelist
          └─ Response as Invention DNA JSON
```

- APIキーをQuestアプリに埋め込まない。ローカル開発時も環境変数等で管理。
- AIが返したコードをQuest上で直接実行しない。JSON設計図を検証し、登録済みC#機能モジュールにのみ変換。
- LLM失敗時は設計図のサンプルを読み込む。オンライン前提のデモにしない。
- 3D生成AIは必須依存にしない。生成物を使う場合はポリゴン数、材質、可動部、利用規約を検証する。

## 5. 発明DNA（設計データ）

### 5.1 スキーマ例

```json
{
  "schemaVersion": 1,
  "id": "inv-demo-001",
  "name": "ハンズフリー雨よけ装置",
  "category": "protection",
  "purpose": "手で傘を持たずに雨を防ぐ",
  "mode": "dream",
  "parts": [
    {"id":"core", "type":"body", "position":[0,1.6,0], "scale":[0.25,0.12,0.25]},
    {"id":"shield", "type":"canopy", "position":[0,1.85,0], "scale":[1.2,0.12,1.2]}
  ],
  "behaviors": [
    {"type":"follow_head", "parameters":{"heightOffset":0.35}},
    {"type":"rain_shield", "parameters":{"radius":0.6,"effectiveness":0.9}}
  ],
  "constraints": {"maxParts":12,"maxSpeed":3.0},
  "revision": 1,
  "parentRevision": null
}
```

### 5.2 検証ルール

- `schemaVersion`一致、必須フィールドあり、JSON構文正常
- `category` / `type` は許可リストのみ
- `parts`最大12（初期値）、各座標・寸法・速度は範囲内にクランプ
- `id`重複なし、参照先の部品が存在する
- 不明な機能は無視せずエラーとして返し、代替案を提示
- 変更時は旧版を保持し、差分プレビューと取り消しを提供

## 6. AI設計・改良パイプライン

### 6.1 新規発明

1. ユーザーの指示を受信
2. LLMへ利用可能な部品・機能・パラメータとJSONスキーマを渡す
3. JSONのみ受信しスキーマ・許可リスト検証
4. エラーなら修正要求を最大2回実施
5. プレビュー表示、利用者が承認
6. Unity Builderで部品を生成し機能を接続
7. 実験可能状態にする

### 6.2 改良

1. 現在のDNA、直近の計測値、ユーザー指示を送信
2. AIは変更操作（add_part/remove_part/update_parameter）を出力
3. 差分と影響をプレビュー
4. 承認後に適用、旧版を保存
5. 同一条件で再実験し比較

### 6.3 エラー時の動作

- APIタイムアウト：待機を解除し再試行/サンプルへ切替
- 無効JSON：理由をログに記録しユーザーには簡潔に説明
- 未対応発明：対応できる機能を明示し、近い試作品を提案
- 実験が不安定：停止、初期位置に戻す、物理値をリセット
- 通信断：既存発明の試用・保存は継続可能

## 7. 機能モジュール

### 7.1 初期の部品タイプ

`body`, `wheel`, `container`, `sensor`, `arm`, `canopy`, `thruster`, `stabilizer`, `connector`。描画はプリミティブ/簡易メッシュから開始。

### 7.2 初期の動作モジュール

| ID | 動作 | 主要パラメータ |
|---|---|---|
| follow_user | ユーザー追従 | speed, followDistance |
| avoid_obstacle | 障害物回避 | detectionRange |
| carry_load | 積載 | capacity |
| hover | 浮遊 | lift, maxHeight |
| move_forward | 推進 | thrust, speedLimit |
| stabilize | 姿勢安定 | stabilizationStrength |
| follow_head | 頭上追従 | heightOffset |
| rain_shield | 雨よけ判定 | radius, effectiveness |

**注意：** 雨よけは雨粒の衝突判定・簡易被濡れスコアで検証する。実物の空気流体解析ではない。飛行もゲーム物理であり、現実の飛行性能予測ではない。

### 7.3 発明カテゴリ

- **protection（必達）**：ハンズフリー雨具。雨粒・風向き・被濡れスコアを評価。
- **carrier（第2優先）**：追従運搬ロボット。追従誤差・衝突数・到達時間を評価。
- **mobility（第3優先）**：空飛ぶ靴。移動・浮遊・安定度を評価。酔い対策として観察モードも用意。

## 8. DREAM / REALITY MODE

### DREAM

自由な浮遊・理想化した防護・高い出力など、ゲーム的な能力を許可。画面に「空想シミュレーション」と常時表示。

### REALITY

仮定した重量、出力上限、風、摩擦、バッテリー容量等の制約を適用する。実際の物理・工学的精度を保証しない。「簡易モデルによる参考値」と表示し、現実に適用するには専門検証が必要であることを明記する。

### 比較

同一の発明DNA・初期位置・環境シードで両モードを実験し、移動距離、被濡れスコア、消費エネルギー等の差を表示する。異なるモードで計算式が異なることを説明する。

## 9. 実験世界と計測

### 9.1 実験プリセット

- RainLab：雨量・風向・風速・遮蔽物
- ObstacleCourse：障害物の配置・移動距離
- FlightDeck：重力・風・目標地点

環境は事前作成したモジュールを配置して構築する。3か月版では世界全体の自由生成は不要。

### 9.2 テレメトリ

`experimentId`, `inventionId`, `revision`, `mode`, `environment`, `seed`, `startTime`, `durationSec`, `metrics`, `notes`。実験履歴はローカル保存。ユーザーの発言・音声は明示的な同意なく記録しない。

### 9.3 比較の例

雨具：`wetnessScore`（低いほどよい）、`coverageRatio`（高いほどよい）。運搬：`collisionCount`、`averageFollowDistance`。移動：`completionTime`、`stabilityScore`。指標の計算式はコードと発表資料に明記する。

## 10. Reality Bridge

発明ごとに「現実の目的」「現在の既知技術で近いもの」「未解決の課題」「簡易モデルの仮定」「追加検証が必要な事項」を表示。LLMの回答を事実として断定しない。現実の製品化・安全性評価は行わない。技術的な根拠が不明な場合は「要調査」とする。

## 12. API設計（例）

- `POST /api/inventions/design`：`{requestText, availableParts, availableBehaviors}` → `InventionDNA`
- `POST /api/inventions/revise`：`{dna, requestText, lastExperiment}` → `RevisionProposal`
- `GET /api/health`：稼働確認

通信はHTTPS、入力長制限、リクエスト制限、APIキーのサーバー管理、ログからの個人情報除去を実施。外部AIへの入力内容をUIで説明する。レスポンスのJSON検証はサーバーとUnityの両方で行う。

## 14. 品質・性能・テスト

- Quest実機で計測。目標フレームレートは端末・設定に応じて72fpsを目安とし、維持できることを優先。
- 描画負荷の高いリアルタイム生成・粒子数を制限。オブジェクトプールを使用。
- VR移動はテレポート優先。飛行時は固定視点の観察モードも提供。
- API不通でも保存済みサンプルで全デモを完走できる。
- JSONの不正値、部品欠落、通信タイムアウト、連続改良、保存/復元をテスト。
- 初心者3〜5名以上を目安に試用テストを実施し、操作時間・詰まった箇所・楽しさを記録（可能な範囲で）。

### 受入テスト（最低限）

1. 「手を使わず雨を防ぐ装置を作って」で雨具が構築される。
2. 雨具を起動し、雨量・風向の変更で被濡れスコアが変わる。
3. 「防ぐ範囲を広げて」で設計差分が表示され、承認後に性能が変わる。
4. DREAM/REALITYを切り替え、両方の前提と結果を比較できる。
5. 保存・終了・再起動後に同じ発明DNAが復元される。
6. AI通信を遮断してもサンプル発明でデモを継続できる。

## 15. 研究評価と発表

### 研究課題

「生成AIとVRを組み合わせた自然言語による機能付き仮想試作品の生成・試用・改良は、初心者のアイデア具体化を支援できるか」

### 評価指標

- 指示から試作品完成までの時間
- 指定機能の実装成功率（あらかじめ定義したテスト指示）
- 試用後に発見した問題数と改良完了率
- 利用者の操作負担・楽しさ・再利用意向（簡単な質問票）
- 可能ならデスクトップ3D操作との比較。ただしサンプル数が少ない場合は探索的結果として扱う。

### 発表デモ（約3〜5分）

1. 日常の不便を提示：「両手がふさがっていて傘を持てない」
2. AIに日本語で発明指示 → 設計プレビュー → VR内で組み立て
3. 雨を降らせる → 風を強める → 雨が当たる
4. 「横からの雨も防いで」 → 防護範囲の変更
5. 再実験 → 数値比較
6. DREAM/REALITYを切替 → 現実化の課題を提示
7. 社会課題と今後の発展を説明

ネットワークやAIの応答に備えて、同じ流れを再生できる録画と固定サンプルを用意する。

## 16. 既存技術との差別化調査（実施タスク）

実装初期に、VRモデリング、生成3D、自然言語3D編集、VRプロトタイピング、AI設計支援の既存サービス・研究を調査し、以下の軸で比較表を作成する：①自然言語入力、②機能付き生成、③VR試用、④実験計測、⑤自然言語改良、⑥現実化の制約説明。未調査の段階では「世界初」「誰もやっていない」と表現しない。

## 17. 想定リスクと対応

| リスク | 対応 |
|---|---|
| 生成3Dが動作に適合しない | 固定機能骨格＋簡易外観を優先 |
| LLMが不正な設計図を返す | JSONスキーマ・ホワイトリスト・再試行 |
| Questで描画が重い | 低ポリゴン・粒子削減・実機計測 |
| API費用や回数制限 | キャッシュ、サンプル設計、呼び出し上限 |
| 現実の物理を誤解させる | 簡易モデルと仮定を常時明示 |
| 12週間で完成しない | 雨具1カテゴリの縦切り完成を最優先 |
| VR酔い | テレポート・固定視点・スナップターン |
| 発表中に通信障害 | オフラインサンプルと録画を用意 |

## 18. 開発エージェントへの初回指示文

## 21. デザインシステム（実装必須）

### 21.1 世界観
- 「現実の最先端研究所 × 可動式SF機構」。白系コンクリート、マット金属、ガラス、工業設備、天井照明、ロボットアーム。
- 中央の円形発明台を視覚的な主役とし、周囲に実務的な作業台、格納棚、導線を配置。

### 21.3 VR UI原則
- **PCゲームの全面固定HUDをVR視界に貼り付けない**。参考画像の上部ナビゲーションは、VRでは研究室の固定サイン／手元のメニューに変換。
- 主入力パネルは発明台前方のWorld Space UI。正面約1.2mを初期配置目安とし、身長・座位で再配置できること。
- 片手でメニューを呼び出せる。操作はQuestコントローラーのレイ＋トリガーで完結。手追跡は将来拡張。
- ロコモーションはテレポート＋スナップターンを標準。座位・立位を切り替え、リセンター操作を用意。
- AI応答中、通信切断、失敗、保存完了は明示。取り消し・戻る・再試行を設ける。
- 激しい飛行・カメラ強制移動を避け、飛行装置のデモは第三者視点／固定プラットフォーム観察モードを初期設定とする。

## 23. 6画面の状態・操作・遷移仕様

### S01 発明指示（採用済み画面）
- 中央：AI INVENTOR、発明台、音声/テキスト入力。左右：研究室の説明、発明フロー。
- 下部：クイック発明例（空飛ぶ靴／追従ロボット／ハンズフリー雨具）。
- **送信** → 入力検証 → `GeneratingDesign`。空入力・長すぎる入力は警告。音声が使えなくてもサンプル選択とテキストで進める。
- クイック発明は即時に設計処理を開始するのではなく、入力欄へ反映して確認可能にする。

### S02 AI設計・生成
- 段階表示：意図解析 → 機能選定 → 部品設計 → 組み立て → 完成。進捗は実際の処理ステージに紐づける。根拠のない「72%」などの擬似進捗は表示しない。
- 中央：ワイヤーフレーム/仮モデルから部品が順番に出現。右：採用機能と部品。左：ユーザー指示と確認事項。
- AI設計JSON検証に成功 → 設計プレビューと承認 → `Building` → `Editing`。失敗時は理由、再試行、サンプル設計の選択を表示。

### S03 発明品編集
- 中央：完成した機能付き3D道具。左：外観プリセット/部品一覧。右：対応パラメータ（範囲・単位・制限を明示）。
- `AIに改良を依頼`、`元に戻す`、`実験へ`。編集は履歴に記録。未対応機能の要求は代替案を提示し、黙って無視しない。

### S04 実験環境設定
- DREAM / REALITY の切替。環境プリセット（雨・風・障害物）と対応パラメータ。非対応の組み合わせは選択不可。
- `実験開始` → 設定スナップショット保存 → `RunningTest`。REALITYは**限定モデル**である旨を常時表示。

### S05 実験結果・AI改良
- 結果は実測したUnityシミュレーション値のみ表示。例：被濡れスコア、運搬達成率、障害物接触回数。架空の総合点や精度率は表示しない。
- 改良前後の同一条件比較、前提・測定方法・限界、改善案。`改良して再実験`でS03に戻る。

### S06 発明品保存・ギャラリー
- ローカル保存した発明DNAをカードで表示。名称、カテゴリ、更新日時、バージョン、実験済みマーク。
- 読込、複製、削除（確認ダイアログ）、戻る。共有/公開はMVPでは非対応と明示。

### 23.1 状態遷移
`Idle → Drafting → GeneratingDesign → AwaitingApproval → Building → Editing → ConfiguringTest → RunningTest → ReviewingResult → Editing / Saved`。
全状態で `Error` / `Cancelled` に遷移可能。保存はEditing/ReviewingResultから可能。二重送信防止、非同期操作のキャンセル、UI状態の一元管理を必須とする。

### 24.2 重要インターフェース
- `IInventionDesignService.GenerateAsync(request, cancellationToken)` → 検証可能なDNA。ネット接続失敗時は明示的なオフライン選択へ。
- `IInventionBuilder.Build(validatedDna)` → Unity GameObject + 結果/警告。入力を必ず検証。
- `IExperimentRunner.Run(config, invention)` → 再現可能な計測結果。乱数シードを記録。
- `IInventionRepository.Save/Load/List/Delete` → JSONのスキーマバージョンと安全なファイル名管理。
- `IAppStateMachine.Transition(action)` → 画面遷移・多重操作の制御。

### 24.3 AI・セキュリティ・信頼性
- AI出力は**データのみ**。実行可能なC#、任意スクリプト、任意アセットパス、任意URLを生成結果から実行・ロードしない。
- JSONはスキーマ検証・enumホワイトリスト・数値範囲制限・部品数上限・最大文字数を設ける。未知フィールドは拒否または明示的に無視。
- APIキーはQuest APKやGitに含めない。開発用プロキシ/サーバー側で保持。API未設定でもローカルサンプルで全デモを完走可能にする。
- APIタイムアウト、再試行上限、コスト上限、通信失敗時の画面を実装。ログには秘密情報・音声全文を無断で保存しない。
- Unity・XR・Androidの**実際のインストール済みバージョン**を調査してからAPIやパッケージを選ぶ。未検証のバージョン固定や存在しないAPIの記述は禁止。
- LLMによるREALITY説明は推定・仮定を表示し、工学的な安全性や実現性の保証をしない。

### 24.4 UIの実装契約
- World Space Canvas + TextMeshPro相当で操作可能なパネルを作る。画像参照はレイアウト・材質の参考であり、画像を貼っただけの疑似UIは禁止。
- デザイン定数は `LabTheme` 等に集約。画面固有の色のハードコードを避ける。
- 各画面に `Loading / Empty / Error / Success` の状態を定義。エラー時も戻れる。
- キーボード入力がQuest単体で難しい場合、事前入力サンプルを正式フォールバックとし、PC開発用UIは別途設ける。

## 27. 完了報告ルールと最初の開発タスク

Claude Codeは作業開始前に `docs/IMPLEMENTATION_STATUS.md` に環境調査結果、既存コードの構成、変更予定、テスト方針を記録する。1タスクごとに変更ファイル、動作確認方法、実施したテストと結果、未検証事項、次のタスクを記録する。Unity Editor/Questを実際に起動していない場合は**動作確認済みと報告しない**。

最初の実装順序：
1. リポジトリを調査し、既存Unityプロジェクトを壊さない作業計画を作成。
2. Unityバージョン・XRパッケージ・Androidビルド設定を確認。
3. DesignReferencesを読み、中央研究室のグレーボックスとWorld Space発明入力UIを作成。
4. サンプル雨具DNAの型・バリデーション・生成・保存を実装。
5. 雨の実験の計測とパラメータ変更を実装。
6. 自然言語API接続は**サンプルで動くループが完成してから**追加。

**本書は実装指示として利用可能だが、Unityプロジェクト・API資格情報・実機へのアクセスなしに自動的な完成を保証するものではない。**
