# 発明の公開と採用（IMPOSSIBLE LIBRARY）設計

作成：2026-11-25 ／ 状態：9章の1（依頼文と改良の依頼文の保存）・2（GLB の書き出し）・3（PC 側の入口）を実装、4 以降は未実装。元の構想は `docs/MONETIZATION.md` の3章（発明ライブラリ）。

## 1. 見せる流れ

1. 利用者が VR で発明・実験・改良し、保存の画面で公開する（同意の画面を通る）。
2. PC 上のサイト IMPOSSIBLE LIBRARY に、その発明のページが載る（回せる3D・実験の結果・改良の履歴つき）。
3. ほかの利用者がサイトで、または VR で呼び出して試して、ほしいを押す。
4. 登録した研究者か開発者が、発明を読み、理由を書いて採用する。
5. 採用の知らせが Quest に届く。発案者と採用した人が、サイトと VR（音声で返事）でやりとりする。

実際の研究・開発は見せない。デモは採用されてやりとりが始まるところで終わる。

## 2. 決めたこと（2026-11-25）

| 項目 | 決定 |

| 読む人 | 研究者と開発者の両方。前半は共通、後半を立場ごとに分ける。サイトに入るときに立場を選ぶだけ |
| 依頼文 | 最初の依頼文を原文のまま載せる。公開前の確認の画面で原文を見せる |
| 試作品 | サイト上で回せる3D。Quest で公開するときに試作品を glTF（GLB）に書き出して送る |
| 改良の履歴 | 結果が変わった版と、最初と最後の版だけ |
| 失敗した実験 | 載せる。最後の版の失敗は、残っている課題として出す |
| 権利と同意 | 文面と同意の操作だけ（法的な確認はしていないデモ用の文面） |
| サイトの名前 | IMPOSSIBLE LIBRARY（研究所で生まれた発明が並ぶ図書館） |

## 3. 公開ページの中身

### 共通（前半）

| 欄 | 中身 | 元のデータ |
|---|---|---|
| 見出し | 名前、ひとことの概要、状態（公開中・検討中・採用）、発案者の表示名、公開日 | 設計の名前と概要、公開の記録 |
| 困りごと | 依頼文の原文、誰がどんな場面で困っているか、要望の一覧 | 新しく保存する依頼文、概要、要望の一覧 |
| 試作品 | 回せる3D。部品を選ぶとその部品が光り、役割が出る | 書き出した GLB、部品の役割 |
| しくみ | 要望ごとに、どの部品とどの機能で実現するか | 製品の説明のしくみ |
| 実験 | 実験ごとの条件・数値・合否（失敗も）、改良前後の比較 | 実験の記録 |
| 改良の履歴 | 結果が変わった版ごとに、何を変えたか・なぜ・結果がどう変わったか | 版どうしの差分、新しく保存する改良の依頼文 |

### 研究者向け（後半）

- 確かめられなかったこと（確かめられない要望と、その理由）
- 計算の前提と仮定、実験の条件と再現の情報（シード・係数の出典）
- 単純化して測ったこと（何を扱っていないか）

### 開発者向け（後半）

- 部品の構成（種類・寸法・素材・推定の重さ）、総質量、倒れる角度などの計算値
- REALITY の推定（電力・使える時間）
- 現実にするための課題と、近い既存の技術

### 採用

- 研究者：研究テーマとして取り上げる。開発者：製品化を検討する。
- 採用できるのは登録した研究者・開発者だけ。押すときに理由をひとこと書く（必須）。採用は何件でも受け付け、ページに採用した人（名前・所属・立場・確認済みの印）を並べる。
- 状態は 公開中 → 検討中（だれかが「検討中」を押した）→ 採用 の3つ。取り下げたものは一覧から消える。

### 需要

- ほしい人の数を2つに分けて出す：VR で試してほしいを押した人の数（需要の証拠として大きく出す）と、サイトで読んでほしいを押した人の数。
- VR で試した人数も出す。
- 1人1回まで（サイトはブラウザごと、VR は端末ごと。デモなので厳密な重複の防止はしない）。
- 見本の発明に入れておく数は、見本であることと合わせて明記する。

### 身元と登録

- **研究者・開発者**：名前・所属・立場（研究者か開発者か）・専門の分野・ひとことの紹介を登録する。採用した発明の一覧がその人のページに出る。
- **確認済みの印**：運営が所属を確かめた人に付ける。デモでは運営の画面で印を付けるだけで、本物の確認はしないことを画面に書く。
- **発案者**：Quest ごとに発案者の ID を作る。公開ページでは表示名か匿名を発明ごとに選べるが、発案者のページ（表示名・公開した数・採用された数）は表示名で公開したものだけで作る。
- ログインは形だけ（立場とアカウントを選ぶだけ。パスワードは作らない）。

### やりとり

- 採用されると、その発明について、採用した人と発案者の2人だけが読める連絡の場ができる（採用した人ごとに1つ）。
- 発案者はサイトの発案者のページか、VR の保存の画面から読める。VR では音声で返事を入れ（今の音声入力と同じく PC の中で文字にする）、送る前に文字で確かめる。
- 発案者が匿名で公開していても、やりとりはできる（相手に見えるのは、発案者が自分で書いた内容だけ）。

## 4. VR 側（Quest のアプリ）

- **保存の画面**に「公開する」を足す（保存済みで、実験を1回以上した発明だけ）。
- **公開の確認**（1画面）：依頼文の原文、載せるもの・載せないもの、表示名（匿名か表示名か）を見せる。
- **同意**（1画面）：同意の文面の短い版（6章）を見せ、「同意して公開する」「やめる」。
- **送信**：公開データと GLB を PC に送る。失敗したら理由を出し、保存の画面に戻る。
- **公開後**：ギャラリーと保存の画面に状態（公開中・検討中・採用）を出す。採用されたら、次に開いたときに知らせを1回出す（採用した立場・理由のひとこと）。
- **取り下げ**：保存の画面から公開をやめられる。
- **やりとり**：保存の画面から、採用した人ごとの連絡を読み、音声で返事を送れる。
- **ライブラリを試す**：ギャラリーに IMPOSSIBLE LIBRARY の一覧を出し、ほかの人の公開した発明を呼び出して、発明台に出して試用・実験できる（自分の保存データにはしない）。試したあとに、ほしいを押せる。

### 新しく保存するデータ

- 最初の依頼文（設計を作った依頼の文）。今は保存していない。
- 改良を頼んだ文（版ごと）。今は保存していない。
- 公開の記録（公開 ID・公開日・表示名・状態）。

前に保存した発明には依頼文と改良の理由が無いので、ページには「記録なし」と出し、何を変えたかは版どうしの差分から作る。

保存の形（実装済み）：保存ファイルに `requestText`（最初の依頼文、400 文字まで）、`designSource`（ai / offline）、`revisionNotes`（版ごとに `revision`・`parentRevision`・`source`〔ai / offline / manual〕・`request`〔改良を頼んだ文。手動の調整では空〕・`summary`・`changes`〔項目・前・後〕・`at`）を足した。元に戻した版の記録は消え、作り直した同じ番号の版は置き換わる。欄が無い・形が合わない記録は、その欄だけ空として読み、発明そのものは読める。

音声で入れた依頼文も文字として PC に送るが、PC の外には出さない。PC のプログラムの記録（ログ）には依頼文を書かない。

## 5. 3D の書き出し

- 立体表示のために組み立てている試作品の写し（角の丸み・塗り分けを当てたもの）から、部品ごとの頂点・法線・面・色を GLB にまとめる。
- 書き出しは C# で書き、外部のパッケージは使わない（Mesh の頂点・法線・三角形を読むだけ）。
- 部品の名前に部品の ID を入れ、サイトで部品を選ぶと光らせる。
- 大きさの目安：1件で数百 KB 以内（Quest から USB 経由で送る）。

実装（`Core/GlbWriter.cs`・`Runtime/ProductExport.cs`）：DNA から見えない場所に写しを組み立て、部品ごとに1つのノード（名前と `extras.partId` が部品の ID、DNA の順）にまとめる。頂点は発明の根元を原点にした座標に焼き込み、glTF の右手系へは X を反転して三角形の順を逆にする。材質は URP の色・金属・なめらかさ・発光・半透明から作る（色は線形に直す）。センサーの光のにじみの板は入れない。雨よけの側面の覆いは雨よけの部品に入れる。大きさの上限の目安は 600 KB。

## 6. 同意の文面（デモ用の案）

### 公開の前に出す短い版（VR の同意の画面）

> この発明を発明ライブラリに公開します。
> 研究者と開発者が読み、研究や開発の検討に使えるようになります。
>
> - 公開するもの：依頼文、試作品の3D、実験の結果、改良の履歴、表示名
> - アイデアの権利はあなたに残ります。採用されたら連絡が届き、その先の条件は別に話し合います
> - 公開すると、特許が取りにくくなることがあります。特許を考えているなら、公開の前に専門家に相談してください
> - 試作品と実験は簡単な計算によるもので、安全や性能は保証しません
> - 設計には AI の手伝いが入っています
> - 公開はいつでも取り下げられます
> - 採用されると、相手とあなただけが読める連絡の場ができます
>
> 18歳未満の人は、保護者の同意を得てから公開してください。

ボタン：「同意して公開する」「やめる」。全文はサイトの利用規約のページに載せ、短い版の下に「全文はサイトの利用規約にあります」と書く。

### 利用規約（サイトに載せる全文）

1. **公開される範囲**
   公開すると、依頼文の原文、試作品の3D、部品の構成と役割、しくみ、実験の条件と結果（合格しなかったものを含む）、改良の履歴（結果が変わった版）、表示名が、発明ライブラリのだれでも読めるページに載ります。保存してあるほかの発明、音声そのもの、端末の情報は載りません。
2. **発案者の表示**
   公開するときに、表示名で載せるか、匿名で載せるかを選べます。匿名の場合は「発案者」とだけ表示します。
3. **権利の扱い**
   発明のアイデアの権利は、発案者に残ります。研究者と開発者は、公開された発明を読み、研究や製品化の検討に使えます。検討を超えて製品として作る場合は、発案者との話し合いが必要です。
4. **採用・製品化されたとき**
   研究者か開発者が採用すると、発案者に知らせが届きます。製品化に進むときの条件（対価や名前の表示）は、発案者と相手が別に話し合って決めます。
5. **特許の注意**
   公開すると、その内容は新しい発明として扱われにくくなり、特許を取りにくくなることがあります。特許を考えている場合は、公開の前に専門家に相談してください。
6. **取り下げ**
   発案者は、いつでも公開を取り下げられます。取り下げると、ページは一覧から消えます。取り下げる前に読まれた内容を、読んだ人の記憶から消すことはできません。
7. **安全と性能を保証しないこと**
   試作品と実験は、仮想の空間での簡単な計算によるものです。実際の安全・性能・法令への適合を保証しません。現実に作るときは、別に設計と試験が必要です。
8. **AI が設計を手伝ったこと**
   設計・実験の計画・説明の文には、AI が作ったものが含まれます。内容が正しいとは限りません。
9. **載せてはいけないもの**
   個人を特定できる情報、他人の権利（特許・著作権・商標など）を侵すもの、人や動物を傷つける道具、法令に反する使い方を目的とするものは公開できません。運営は、これに当たる公開を取り下げることがあります。
10. **18歳未満の場合**
    18歳未満の人は、保護者の同意を得てから公開してください。
11. **採用した相手とのやりとり**
    採用されると、採用した研究者・開発者とあなただけが読める連絡の場ができます。相手に見えるのは、公開ページの内容と、あなたがやりとりの中で書いた内容だけです。連絡先や本名を伝えるかどうかは、あなたが決めてください。運営は、規約に反する使い方を確かめるために、やりとりの内容を読むことがあります。

この文面はデモ用の案で、法律の専門家の確認はしていない。

## 7. PC 側（AI 中継のプログラムに足す）

| 入口 | 内容 |
|---|---|
| `POST /library` | 公開データ（JSON）と GLB を受け取り、`proxy/library/` に保存する。公開 ID を返す |
| `GET /library` | 一覧（取り下げたものを除く） |
| `GET /library/:id` | 1件の公開データ |
| `GET /library/:id/model.glb` | 3D |
| `POST /library/:id/adopt` | 採用（立場・理由） |
| `POST /library/:id/withdraw` | 取り下げ（発案者の端末から） |
| `GET /library/status?ids=` | Quest が自分の公開の状態と採用の知らせを取りにくる |
| `POST /library/:id/want` | ほしい（サイトから、または VR で試したあと） |
| `POST /library/:id/tried` | VR で試した（呼び出して試用か実験をした） |
| `GET/POST /accounts` | 研究者・開発者の登録と一覧、確認済みの印（運営の画面から） |
| `GET/POST /threads/:id/messages` | 採用した人と発案者のやりとり |

- サイトの画面も同じプログラムから出す（`http://127.0.0.1:8787/` を PC のブラウザで開く）。
- `proxy/library/` は git に入れない。
- 受け取るデータは形と大きさを確かめてから保存する（文字数・ファイルの大きさの上限）。

実装（`proxy/src/library/`：`schema.ts`・`store.ts`・`routes.ts`、入口の一覧は `proxy/README.md`）で決めたこと：
- 公開のデータは Quest が表示する文と計算済みの値（部品の寸法・推定の重さ・倒れる角度・電力など）まで作って送り、PC は形と大きさだけを確かめる（`schema.ts` の `Publication`）。GLB は base64 で同じ要求に入れる（2MB まで、GLB は 1MB まで）。
- 発案者の端末の鍵（`x-ilab-creator`）は Quest ごとに作って Quest に残す。PC はハッシュだけを持ち、公開ページには鍵から作った発案者の公開 ID（表示名で公開したときだけ）を出す。同じ端末の同じ発明を公開し直すとページを更新し、ほしい・採用の数は残る。
- 状態：取り下げた発明は一覧から消え、ページは 410。運営が取り下げたものは公開し直せない。
- 採用：登録した研究者・開発者だけ。理由は必須（200 文字）。同じ人が同じ発明を2回採用することはできない。採用した人ごとにやりとりの場を作る。やりとりは2人以外には「見つからない」と返す。
- サイトと運営の入口は 127.0.0.1 からだけ。Quest の入口は `ILAB_PROXY_TOKEN` を設定したとき（LAN に出すとき）トークンも要る。

## 8. サイト

- 一覧：発明のカードではなく、困りごとの文と試作品の小さい3D（または撮った画像）を並べる。並び順（ほしい人の多い順・新しい順・発案者の採用実績順・名前順）を選び、機能のタグ・使う場面のタグ・状態で絞り込む。
- 使う場面のタグ（生活・仕事・娯楽・移動・健康・屋外など）を新しく作り、設計のときに AI に付けてもらう。前に保存した発明は機能のタグから仮に決める。
- 研究者・開発者のページ、発案者のページ、やりとりの画面、運営の画面（確認済みの印・取り下げ）。
- 1件のページ：3章の順。立場は画面上部で切り替え、後半の欄が変わる。
- 見本：見本の発明を何件か「見本」と明記して載せ、一覧が空にならないようにする。
- デザイン：AI っぽい見た目の禁止事項に従い、design-taste-frontend の機械チェックに合格してから出す。

## 9. 作る順番

1. 依頼文と改良の依頼文を保存する（今から保存しないと、公開するデータが育たない）
2. GLB の書き出しと、その確認（Editor で書き出してブラウザで表示）
3. PC 側の受け取り・保存・一覧・採用・ほしい・登録・やりとりの入口と、そのテスト
4. サイトの一覧・1件のページ・登録・採用・やりとり・運営の画面
5. VR 側の公開の確認・同意・送信・状態の表示・採用の知らせ
6. VR 側のやりとり（読む・音声で返す）
7. VR 側でライブラリの発明を呼び出して試す・ほしいを押す
8. 使う場面のタグ（AI への指示と、前の発明の仮の割り当て）
9. 見本の発明・見本のアカウントの公開データ
10. 通し確認（公開 → ほしい → 採用 → やりとり → Quest に知らせ）と、Quest での実演の確認
